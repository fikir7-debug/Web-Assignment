Time boxing explained

A time box is a fixed, non-negotiable period in which a team commits to finishing a chosen piece of work. When time runs out, the box closes. Unfinished work is re-prioritized, not extended.
FIXEDTime
FLEXIBLEScope
Set the goalWhat must this box deliver?
Fix the duration1 to 4 weeks, never extended
Prioritize scopeMoSCoW: Must, Should, Could, Won’t
Work and track dailyStand-ups, task board, burndown
Review and reflectDemo the result, hold a retrospective

Time boxing in action

Above the dashed line means behind plan. On day 10 the box closes either way.

Benefits

• Focus and urgency

• Predictable delivery dates

• Early, frequent feedback

Pitfalls

• Rushed work from bad estimates

• Quality or testing gets cut

• Constant pressure, burnout

Crystal: a family of methods

Created by Alistair Cockburn in the 1990s. Crystal is people-centered: it tunes how heavy the process is to the team and the project, and favors communication over documentation.

Two dials

Team size: more people, darker color

Criticality: what is at risk if it fails, from comfort to money to life

Clearup to ~6 people
Yellowup to ~20 people
Orangeup to ~40 people
Redup to ~80 people
Team size grows, process gets heavier

Seven properties of success

1Frequent delivery

Ship working software often

2Reflective improvement

Pause to review and adjust

3Osmotic communication

Info flows by working side by side

4Personal safety

Speak up without fear of blame

5Focus

Clear priorities, time to work

6Easy access to expert users

Quick feedback from real users

7Technical environment

Automated tests and integration

Crystal Clear

requires the first three (orange). The rest are strongly recommended.

The prototype process model

Gather requirementsbasic, rough needs only
Quick designfocus on what users will see
Build prototypea small working version
User evaluationusers try it and give feedback
Refinefix the design, loop back to step 3
Build final systemengineer it properly
↺ Refine and repeat from step 3 until users are happy

Best when

• Requirements are unclear

• The user interface is central

• Users can’t say what they want

Watch out

• Users mistake it for the product

• Endless feedback, scope creep

• Quick-and-dirty code carried over

Types of prototyping

1Throwaway (rapid)

Built fast to clarify requirements, then thrown away. The real build starts fresh.
Prototype›Learn›Discard

2Evolutionary

One prototype is refined again and again until it becomes the final system.
Version 1›Version 2›Final system

3Incremental

The system is split into parts. Each is prototyped separately, then merged.
Part A›Part B›Merge

4Extreme

Used mainly for web applications and built in three phases.
Static pages›Services›Real backend

More autonomy means more need for human oversight

The agentic SDLC, phase by phase

1Plan

Agent: drafts user stories

Human: approves requirements

2Design

Agent: proposes architecture options

Human: picks the design

3Build

Agent: writes code, opens PRs

Human: reviews and merges

4Test

Agent: generates and runs tests

Human: checks edge cases

5Deploy

Agent: runs CI/CD, flags risks

Human: approves the release

6Operate

Agent: monitors logs, suggests fixes

Human: decides on changes

Agents act. Humans decide.

Benefits and risks

Benefits

• Faster delivery of routine work

• Continuous checks catch errors early

• Engineers focus on design and decisions

• Quicker feedback across the lifecycle

Risks

• Hallucinated or insecure code

• Over-reliance and skill loss

• Unclear accountability

• Data privacy and IP exposure
